## Cache cliente de TanStack Query (V-02.07 F-PERF-008)

### Alcance

Auditoria V-02.02 (`AUDITORIA_GENERAL_MAVIS_V-02-02.md:220`) recomendo
introducir un helper `useFetcher` con `AbortController` para todos los
listados y un cache de Dashboard a 30 s. La auditoria frontend reciente
(78 `api.get` en `frontend/src/**`, ver `DOCUMENTACION_CAMBIOS.md` entrada
del 2026-07-28) confirmo que las paginas del `<Outlet>` se desmontan al
navegar y que `StrictMode` duplica los efectos de montaje sin
deduplicacion. Esto generaba storms al volver a una pantalla, re-fetch
de agregados de dashboard al alternar entre `Dashboard`, `Titulares` y
`Cuentas`, y re-fetch del resumen de cuenta al paginar.

Se adopta `@tanstack/react-query@^5.59.0` como capa de server-state en
memoria. Es la opcion minima coherente con los 78 GET y 78 mutaciones
existentes: una cache artesanal distribuida por componentes terminaria
siendo peor que la libreria. Se mantiene Axios y sus interceptors
(cola de refresh JWT, CSRF, toast de 5xx/red caida) tal cual.

### Cambios

1. **Dependencia**: `@tanstack/react-query@^5.59.0` añadida a
   `frontend/package.json` y al `package-lock.json`. Bundle adicional

## Cierre #16 - React Router SSR deserialization (GHSA-337j-9hxr-rhxg) + #17 open redirect (GHSA-wrjc-x8rr-h8h6)

### Alcance

Vulnerabilidades #16 y #17 del registro de seguridad. React Router 6.30.4

## Cache de lecturas repetidas del dashboard

### Alcance

Recomendacion del check-list de rendimiento:

> "Cache repeated read queries. Identify read queries that run very
> frequently with the same or few distinct parameters and return data
> that changes slowly. Add a caching layer in front of them with keys
> based on the query parameters and TTLs matched to the data's
> volatility, plus invalidation on relevant writes. Ensure cache misses
> populate safely under concurrency. Verify database query volume for
> these reads drops sharply and response times improve."

Implementacion acotada al dashboard y al catalogo de tipos de cambio.
No se cachean respuestas HTTP completas: se cachean los snapshots
internos que ya estaban costando varios SELECTs identicos por carga
del dashboard. Esto evita los riesgos de claves incompletas que
romperian el aislamiento por usuario (`paisId`, `divisa`, `titularId`,
`userId`, `puedeVerDashboard`).

### Cambios

1. **Nueva capa de cache en proceso (`AtlasBalance.API/Caching/`)**:

   - `ICacheService` + `CacheService`: `IMemoryCache` con
     `GetOrLoadAsync<T>` que implementa single-flight (un `SemaphoreSlim`
     por namespace+key) y generaciones (cada escritura bumpea un
     contador por namespace y las claves cacheadas quedan
     automaticamente invalidadas sin enumerar el cache). Sin entradas
     de timeout porque la generacion las invalida antes.
   - `CacheMetricsSnapshot` con hits, misses, loads, single-flight waits,
     invalidations, load failures. Se expone por namespace via
     `ICacheService.GetMetricsSnapshot(string)`. No contiene claves ni
     IDs para evitar leakage a logs.
   - `DashboardCacheInvalidator`: fachada con tres metodos
     (`InvalidateDashboardScope`, `InvalidateDashboardReference`,
     `InvalidateDashboardMetrics`) que invalida los namespaces del
     dashboard de forma centralizada.

2. **Single-flight + generaciones aplicadas a `TiposCambioService`**:

   El catalogo de tasas ya estaba cacheado (`IMemoryCache`, TTL 5 min,
   invalidacion tras guardado manual o sincronizacion API), pero
   `AUDITORIA_CONCURRENCIA_2026-07-10.md:302` (CONC-027) documentaba
   una race benigna entre `InvalidateCache()` y la llamada a `_cache.Set`
   que podia repoblar datos viejos. La nueva implementacion:
   - usa `GetOrLoadAsync` con lock por namespace+key, asi dos requests
     concurrentes con cache miss ejecutan UN solo `SELECT` sobre
     `TIPOS_CAMBIO`.
   - bumpea la generacion del namespace tras cada escritura manual
     (`GuardarTipoCambioManualAsync`) y sincronizacion API
     (`SincronizarTiposCambioAsync`), lo que invalida todas las entradas
     cacheadas sin enumerarlas.
   - tambien invalida el namespace `dashboard_metrics` porque las
     metricas convertidas dependen del catalogo de tasas.

3. **Scope del dashboard cacheado por usuario**:

   `DashboardService.GetAuthorizedScopeAsync` envuelve el calculo en
   `GetOrLoadAsync(new CacheNamespace(ScopeNamespace), userId:N,
   loader, TTL=30s)`. Las tres llamadas paralelas del frontend
   (`/dashboard/principal`, `/dashboard/evolucion`,
   `/dashboard/saldos-divisa`, ver `DashboardPage.tsx:161`,
   `CuentasPage.tsx:313`, `TitularesPage.tsx:195`) ahora resuelven el
   scope UNA vez por TTL. Claves normalizadas (`userId` en formato
   hex) para evitar fuga entre usuarios.

4. **Referencia del dashboard (divisa base + colores) cacheada**:

   `LoadReferenceAsync` cachea la combinacion `divisa_base + colores`
   durante 5 min. La clave es fija por namespace (`default`) y la
   generacion se invalida cuando cambian `DIVISAS_ACTIVAS` o las claves
   de configuracion relevantes (`divisa_principal_default`,
   `dashboard_color_*`).

5. **Metricas del dashboard cacheadas entre endpoints**:

   `GetOrBuildMetricsAsync` envuelve `BuildMetricsAsync` con TTL de
   15 s y clave `userId|paisId|divisa|hashCuentas`. Asi `principal` y
   `saldos-divisa` (que recalculaban lo mismo) ya no duplican el
   trabajo de agregar extractos por cuenta/divisa ni la conversion
   bulk de tasas.

6. **Invalidacion centralizada via `DashboardCacheInvalidationInterceptor`**:

   Nuevo `SaveChangesInterceptor` registrado tras `AuditSaveChangesInterceptor`
   que invalida caches de dashboard despues de un `SaveChanges`
   exitoso si entre las entidades tocadas estan:
   - `Extracto`, `ExtractoColumnaExtra`, `ExtractoDesglose`,
     `Cuenta`, `PlazoFijo`, `TipoCambio`, `DivisaActiva`,
     `Configuracion` (solo claves relevantes) -> invalida metricas.
   - `PermisoUsuario`, `PreferenciaUsuarioCuenta`, `Usuario`,
     `Cuenta`, `Titular`, `Pais` -> invalida scope.
   - `DivisaActiva`, `Configuracion` (claves relevantes) -> invalida
     referencia.

   Asi cualquier ruta de escritura (controllers, jobs Hangfire,
   seeds) queda cubierta sin acoplar `IDashboardCacheInvalidator`
   en cada consumer. Cobertura minima para no inflar AUDITORIAS ni
   invalidar por escrituras no relacionadas (SMTP, secretos, etc.).

7. **Tests** (`backend/tests/AtlasBalance.Caching.Tests/`, proyecto
   nuevo para no tocar el de tests preexistente que arrastra errores
   de compilacion V-02.06):

   - `CacheServiceTests` (6 facts): hits, single-flight con 20
     lectores concurrentes, generacion por namespace, aislamiento
     entre namespaces, race invalidar durante carga, propagacion de
     cancelacion.
   - `CacheIntegrationTests` (3 facts): invalidacion del catalogo de
     tasas tras escritura manual, bump de generaciones al invalidar
     scope y metrics, consistencia del cache de scope tras cambio
     conceptual de permisos.

## Auditoria de autenticacion y sesion: logout invalida el access token, cambiar-password con limite de intentos

### Alcance

Auditoria de `AtlasBalance.API/Services/AuthService.cs` centrada en
`LogoutAsync` y `ChangePasswordAsync`. Dos hallazgos de severidad
MEDIA corregidos, mas dos reparaciones incidentales que bloqueaban la
verificacion por tests.

### Correccion 1 - Logout no invalidaba el access token en servidor

`LogoutAsync` solo marcaba `RevocadoEn` en el refresh token
presentado. No rotaba el `SecurityStamp` del usuario. Como
`UserStateMiddleware` valida en cada request que el claim
`security_stamp` del JWT coincida con el de BD, y ese stamp no
cambiaba, un access token capturado antes del logout seguia siendo
aceptado por la API hasta 60 minutos. El borrado de cookies era solo
del lado del navegador.

Solucion: `LogoutAsync` ahora (a) exige que el refresh token
presentado este vivo (no revocado y no caducado) antes de actuar,
(b) captura el `SecurityStamp` vigente como `previousStamp` y rota
el `SecurityStamp` via `UserSessionState.RotateSecurityStamp`,
(c) revoca todos los refresh tokens activos del usuario, y (d)
re-ancla al stamp nuevo solo los `MfaTrustedDevices` que cumplen las
cuatro condiciones: `RevokedAt == null`, no caducados, del mismo
usuario y `SecurityStamp == previousStamp`.

Consecuencia funcional buscada: cerrar sesion ahora cierra TODAS las
sesiones del usuario en todos los dispositivos. Esto cubre ademas la
ausencia de una funcion de "cerrar sesion en todas partes".

El re-anclaje de `MfaTrustedDevices` es necesario porque esos
dispositivos estan anclados al `SecurityStamp`; sin re-anclarlos,
rotar el stamp habria cancelado el "recordar este dispositivo" en
cada logout, regresionando el comportamiento fijado en V-01.09
("logout conserva la cookie `mfa_trusted`"). El filtro por
`previousStamp` es lo que evita que ese mismo re-anclaje deshaga
otras invalidaciones: un cambio de contrasena, un reset por admin,
una revocacion administrativa o una deteccion de reuso de refresh
token rotan el `SecurityStamp` sin tocar `MFA_TRUSTED_DEVICES`,
dejando esos dispositivos invalidados de forma implicita
(`RevokedAt == null` pero con el stamp viejo). Sin el filtro, un
logout rutinario posterior los readoptaria como confiables otra vez,
anulando esa invalidacion.

El requisito de "refresh token vivo" evita que alguien con una copia
antigua y ya revocada del token pueda forzar el cierre de sesion del
usuario legitimo de forma repetida.

### Correccion 2 - `cambiar-password` permitia fuerza bruta sobre la contrasena actual

La verificacion de `passwordActual` con BCrypt no incrementaba
`FailedLoginAttempts`, no consultaba `LockedUntil` y no registraba
nada en auditoria. Con una sesion robada se podia adivinar la
contrasena actual sin limite de intentos ni rastro.

Solucion: se comprueba `LockedUntil` antes de verificar (responde 423
Locked si la cuenta esta bloqueada, incluso con la contrasena
correcta); al fallar se incrementa `FailedLoginAttempts`, se bloquea
la cuenta 30 minutos al quinto fallo, y se auditan los eventos
`LOGIN_FAILED` (con motivo `password_actual_incorrecta`) y
`ACCOUNT_LOCKED`. Al acertar se resetean el contador y el bloqueo.
Reutiliza las constantes ya existentes `MaxFailedLoginAttempts` (5) y
`LockDuration` (30 min), las mismas del login.

## Segunda tanda de la auditoria de autenticacion: 4 hallazgos BAJOS cerrados

### Alcance

Segunda tanda sobre los 7 hallazgos de severidad BAJA que quedaron
abiertos en `REGISTRO_BUGS.md` tras la auditoria de autenticacion
anterior (bloque previo en este mismo archivo). Se cierran 4, se
cierra 1 mas como diagnostico erroneo, quedan 2 abiertos por decision
deliberada y se anade 1 hallazgo BAJO nuevo detectado por revision
adversarial.

### Correccion 1 - blocklist de contrasenas comunes 93% inefectiva

`Constants/SecurityPolicy.cs` tenia 105 entradas de las que solo 7
eran alcanzables, porque `TryValidatePassword` rechaza por longitud
minima (12 caracteres) antes de comparar contra la lista. Se
reescribio la lista completa: 154 entradas, todas de 12+ caracteres,
sin duplicados (verificado programaticamente: 154 literales, 154
unicas bajo comparacion case-insensitive, 0 por debajo de 12).
Contenido: variantes de 12+ caracteres de las contrasenas mas
repetidas en filtraciones conocidas (top SecLists/rockyou/
Common-Credentials) mas variantes en espanol y especificas de Atlas
Balance.

El `HashSet` `CommonPasswords` sigue `private`; se anadio
`internal static IReadOnlySet<string> CommonPasswordsView` solo para
que los tests puedan recorrerla. Se eligio la vista de solo lectura en
vez de hacer el `HashSet` `internal` porque un campo mutable visible a
todo el ensamblado permitiria que codigo futuro hiciera `Clear()` y
desactivara la blocklist en silencio.

Archivo de tests nuevo `tests/AtlasBalance.API.Tests/SecurityPolicyTests.cs`
(6 facts). El clave es `CommonPasswords_AllEntries_MeetMinimumLength`,
que recorre la lista entera y falla si alguien vuelve a colar una
entrada corta, impidiendo que la lista vuelva a convertirse en codigo
muerto.

HIBP k-anonymity sigue sin integrarse; el comentario del codigo lo
mantiene como la solucion real para produccion.

### Correccion 2 - enumeracion de usuarios por latencia en login

Si el email no existia o la cuenta estaba bloqueada, `BCrypt.Verify`
no llegaba a ejecutarse, asi que esas dos ramas de `LoginAsync`
respondian ~250 ms antes que "password incorrecta" (los mensajes de
error ya eran identicos; la latencia delataba la rama).

Solucion: `DummyPasswordHash` en `AuthService.cs`, un hash BCrypt
derivado de bytes aleatorios generado una vez al arrancar el servicio
(no es un secreto, no corresponde a ninguna contrasena real), con el
mismo `PasswordWorkFactor`. Se verifica contra el en ambas ramas de
`LoginAsync`.

Revision adversarial detecto que la misma mitigacion faltaba en la
rama de cuenta bloqueada de `ChangePasswordAsync`; se aplico ahi
tambien.

### Correccion 3 - sin rehash automatico de BCrypt

No existia `PasswordNeedsRehash`, asi que subir el work factor de
BCrypt en el futuro no habria migrado los hashes existentes.

Solucion: tras un login correcto, si
`BCrypt.PasswordNeedsRehash(usuario.PasswordHash, PasswordWorkFactor)`
es true, la contrasena en claro ya validada se rehashea con el work
factor vigente (unico momento en que el servicio dispone de ella). Se
introdujo la constante `PasswordWorkFactor = 12` dentro de
`AuthService` y se reuso tambien en `ChangePasswordAsync`, que antes
tenia el 12 como literal suelto, para que ambos valores no puedan
divergir con el tiempo.

### Correccion 4 - sesiones sin rastro de cambio de IP

`IpAddress` y `UserAgentSummary` se guardaban en el refresh token pero
nunca se comparaban fuera de la ventana de 5 minutos del challenge
MFA.

Solucion: `RefreshTokenAsync` compara la IP almacenada en el refresh
token con la IP actual y, si difieren, audita el evento nuevo
`SESSION_IP_CHANGED` (`AuditActions.SessionIpChanged`).

Decision explicita: **no se invalida la sesion.** Atar la sesion a la
IP expulsaria a usuarios legitimos con VPN, DHCP o salto de red; atarla
al User-Agent la romperia con cada auto-actualizacion del navegador.
El rastro de auditoria es lo que aporta valor de investigacion sin
romper el uso legitimo.

Se anadio `NormalizeIpForComparison` porque una misma maquina puede
llegar como `10.0.0.1` (via X-Forwarded-For, que esta habilitado) o
como `::ffff:10.0.0.1` (socket dual-mode directo), y
`IPAddress.Equals` los trata como direcciones distintas porque cambia
la familia. Sin normalizar se generarian alertas de cambio de IP
falsas en cada peticion desde la misma maquina.

Solo se compara la IP: anclar tambien el User-Agent exigiria anadir
una columna a `REFRESH_TOKENS` y su migracion; queda fuera de este
alcance.

### Cierre 5 - `MaxAge` de `csrf_token` (diagnostico erroneo, no es bug)

El fallo de CSRF devuelve 403, y el interceptor de
`frontend/src/services/api.ts` solo auto-recupera en 401, 419 y 440.
Si se acortara la cookie CSRF a 1h para igualarla al access token, un
usuario inactivo mas de 1h con el refresh token todavia vivo fallaria
con 403 sin recuperacion automatica en su siguiente operacion. Los 7
dias actuales coinciden con la vida del refresh token, que es la vida
real de la sesion. Comportamiento actual correcto; se deja como esta.

### Hallazgo nuevo (severidad BAJA) - asimetria residual de escrituras a BD en el login

Detectado por revision adversarial durante esta misma tanda. Tras
igualar el coste de BCrypt entre ramas, queda una diferencia menor: la
rama de password incorrecta hace un `SaveChangesAsync` extra para
persistir el contador de intentos, mas su registro de auditoria; las
ramas de email inexistente y cuenta bloqueada no. No se persigue:
igualarla exigiria escrituras ficticias a BD, y la senal (del orden de
milisegundos o menos) queda sepultada bajo el jitter de red normal.

2. Sin tests de frontend para auth: el runner actual es

## Auditoria de mensajes de error sensibles y fugas de datos, con correcciones

### Alcance

Auditoria de mensajes de error y posibles fugas de datos hacia el
cliente: respuestas HTTP de error, `console.*` del navegador, bundle
de produccion (sourcemaps y JS minificado) y el comportamiento por
defecto de ASP.NET Core (`ValidationProblemDetails`,
`WWW-Authenticate`). 10 hallazgos corregidos (1 ALTA, 3 MEDIA, 6
BAJA), 2 defectos preexistentes detectados y dejados como pendientes
(no son fugas de datos), y una decision de producto documentada sin
cambio de codigo.

### Hallazgo 1 (ALTA) - fragmento de clave API del proveedor de IA filtrado al cliente

Cadena completa: el proveedor externo devuelve 401 con cuerpo tipo
`{"error":{"message":"Incorrect API key provided: sk-proj-..."}}`.
`AtlasAiService.ExtractProviderErrorSummary` extraia `error.message` y
lo pasaba por `ShortProviderPayload`, cuyo regex de redaccion esperaba
la credencial pegada a la palabra clave. Probado con el motor de regex
de .NET: con el texto real de OpenAI el regex redactaba la palabra
"provided:" y dejaba `sk-proj-abc123XYZ` (placeholder inventado, no
una clave real) intacto. Ese texto se concatenaba como " Detalle
proveedor: ..." en el mensaje de `IaProviderException`, que
`IaController` devolvia en el campo `error` de un 502 y el frontend
pintaba en un toast. `IaController` es `[Authorize]` a secas:
cualquier usuario autenticado, no solo ADMIN. Se disparaba solo con
que la clave estuviera caducada, mal escrita o revocada.

Correccion aplicada en `Services/AtlasAiService.cs`:

1. Eliminado el sufijo `{detail}` de todas las ramas de
   `BuildProviderHttpErrorMessage` y `BuildProviderResponseErrorMessage`;
   el parametro `providerError` se conserva porque
   `IsOpenRouterDataPolicyError` e `IsOpenRouterModelRestrictionError`
   lo siguen usando para clasificar el tipo de error de OpenRouter.
2. `ShortProviderPayload` redacta ahora tambien por forma de
   credencial, con los prefijos `sk-proj-`, `sk-or-v1-`, `sk-`, `hf_`,
   `gsk_`, `xai-`, `AIza` (cubre OpenAI, OpenRouter, HuggingFace, Groq,
   xAI y Google/Gemini).
3. `AtlasAiService` no tenia logger: se inyecto
   `ILogger<AtlasAiService>` y `LogProviderErrorAsync` ahora escribe
   tambien en Serilog, porque tras quitar el detalle del cliente la
   auditoria (BD) era el unico rastro; con el logger, queda tambien en
   el log de servidor.

Riesgo residual aceptado: si un proveedor usa un prefijo de clave
fuera de esa lista, el fragmento llegaria al log y a la auditoria,
ambos de acceso exclusivo de administrador en maquina on-premise. Se
descarto una redaccion generica por longitud porque destruia el texto
util del error para el usuario.

### Hallazgo 2 (MEDIA) - sourcemaps publicados en produccion

`vite.config.ts` genera `.map` con `sourcemap: 'hidden'`, que solo
omite el comentario `sourceMappingURL` del bundle pero no impide
servir el fichero. `Build-Release.ps1` copiaba `dist` a `api\wwwroot`
con `Copy-Item -Recurse -Force` sin filtrar, asi que cualquiera con
acceso podia pedir `/assets/<chunk>.js.map` y leer todo el TypeScript
original.

Correccion: borrado explicito de los `.map` del `wwwroot` publicado
tras la copia (no se usa `Copy-Item -Exclude` porque no filtra de
forma fiable en copias recursivas), con `-ErrorAction Stop` y una
verificacion posterior que lanza excepcion si queda algun `.map`. Un
fallo aqui debe romper la release, no pasar en silencio.

### Hallazgo 3 (MEDIA) - error boundary volcaba el stack al navegador y reportaba a un endpoint inexistente

`AppErrorBoundary.componentDidCatch` hacia
`console.error('UI section crashed', error, errorInfo)` tambien en
produccion, y `navigator.sendBeacon('/api/telemetria/errores', ...)`
contra una ruta que NO existia en el backend (verificado por grep en
todo `backend/src`). Resultado: el detalle completo acababa en la
consola del cliente y no quedaba ningun registro en el servidor.

Correccion: eliminado el `console.error`. Creado
`Controllers/TelemetriaController.cs` + `DTOs/TelemetriaDtos.cs` con
`POST /api/telemetria/errores`:

- `[AllowAnonymous]`, limite de 20 reportes por IP y minuto via
  `IMemoryCache` con ventana fija.
- Recorte de longitud de todos los campos del payload.
- Saneado de CR/LF contra log forging.
- Respuesta 204 siempre (`sendBeacon` ignora la respuesta; devolver
  detalle daria una via de sondeo).

Los nombres de propiedad del DTO se fijan con `[JsonPropertyName]`
porque el frontend envia camelCase y la politica global de
serializacion es SnakeCaseLower. El payload viaja envuelto en `Blob`
de tipo `application/json` porque `sendBeacon` con un string suelto
manda `text/plain` y no bindea. La ruta se ha anadido a las
exclusiones de `CsrfMiddleware` (`sendBeacon` no puede enviar
cabeceras, luego no puede mandar `X-CSRF-Token`; el endpoint no lee ni
modifica datos) y de `PrimerLoginMiddleware` (el reporte de errores
debe funcionar tambien con cambio de password pendiente).

### Hallazgo 4 (MEDIA) - sin error boundary raiz ni handlers globales

El boundary solo envolvia el contenido de cada ruta en `App.tsx`; un
fallo en el layout, en los providers o en el propio `App` dejaba
pantalla en blanco. No existia ningun `unhandledrejection` ni
`window.onerror`.

Correccion: en `main.tsx`, `AppErrorBoundary` envuelve ahora todo el
arbol por fuera de `QueryClientProvider` y `BrowserRouter`, y se
registran listeners de `unhandledrejection` y `error`. Toda la logica
de envio vive en el modulo nuevo `src/utils/reportClientError.ts`, con
tope de 10 reportes por carga de pagina y sin escribir nunca en
consola.

### Hallazgo 5 (BAJA) - `ValidationProblemDetails` por defecto

No habia `InvalidModelStateResponseFactory`, asi que `[ApiController]`
devolvia el `ValidationProblemDetails` por defecto con `traceId`, la
URL `type` de rfc7231, tipos .NET (`System.Guid`) y nombres de
propiedad C# en PascalCase (`RawData`), distintos del contrato
snake_case.

Correccion: `Program.cs` registra un `InvalidModelStateResponseFactory`
que devuelve 400 con
`{ "error": "Los datos enviados no son validos. Revisa el formulario e
intentalo de nuevo." }` y loguea el detalle real del ModelState en el
servidor con los nombres de campo pasados por `LogScrubber.Scrub`.
Comprobado antes de aplicarlo que el frontend no depende de ello:
`errorMessage.ts` lee `payload.errors` pero degrada limpiamente al
mensaje generico de 400, y no usa `traceId` en ningun punto.

### Hallazgo 6 (BAJA) - `JwtBearer.IncludeErrorDetails`

El default del framework es `true` y hace que el header
`WWW-Authenticate` lleve `error_description` con el motivo y el
timestamp exacto de expiracion. Nunca se habia desactivado.

Correccion: `options.IncludeErrorDetails =
builder.Environment.IsDevelopment();`.

### Hallazgo 7 (BAJA) - `UserStateMiddleware` distinguia el motivo del rechazo

Devolvia cuatro mensajes distintos ("Token de usuario invalido", "La
sesion ya no es valida", "Usuario bloqueado temporalmente por

Correccion: respuesta unica "La sesion ya no es valida. Vuelve a

### Hallazgo 8 (BAJA) - el rate limit de integracion cantaba la cifra exacta

### Hallazgo 9 (BAJA) - el build no eliminaba console

No habia `esbuild.drop`, terser ni `minify`. El primer intento uso

Correccion: `build.rollupOptions.output.minify = { compress: {

## Cierre de los dos defectos pendientes de la auditoria de errores

### Alcance

Los dos defectos que la auditoria de mensajes de error dejo abiertos en
`REGISTRO_BUGS.md`. Ninguno era fuga de datos: los dos eran validacion
que aparentaba existir y no existia, dando falsa sensacion de cobertura
a quien leyera el codigo.

### Defecto 1 - FluentValidation registrado sin ningun validador

V-02.06 cableo `AddFluentValidationAutoValidation()` para cerrar MED-23
(`DTOs sin atributos de validacion`). MED-23 admitia dos vias
alternativas —registrar FluentValidation **o** anadir atributos— y se
aplicaron ambas, pero nunca se escribio ni un solo `AbstractValidator<T>`.
El registro escaneaba el assembly y no activaba nada.

Correccion: retirados el `using`, la llamada de registro en `Program.cs`
y la `PackageReference` de `AtlasBalance.API.csproj`. MED-23 **sigue
cerrado** por la via de los DataAnnotations, que es de donde venia toda
la validacion real; queda constancia en un comentario de `Program.cs`
para que nadie lo reanada creyendo que se reabre.

Punto delicado: `Directory.Build.props` fija
`RestorePackagesWithLockFile=true` y `Build-Release.ps1` restaura en
`--locked-mode`. Quitar el paquete obligaba a regenerar los
`packages.lock.json` de `AtlasBalance.API`, `AtlasBalance.API.Tests` y
`AtlasBalance.Caching.Tests` (los dos de test lo arrastraban de forma
transitiva via `ProjectReference`). El Watchdog no estaba afectado. Sin
ese paso la release habria fallado en el primer `restore`.

### Defecto 2 - `[Required]` sobre `Guid` no-nullable nunca dispara

Afectaba a tres DTOs, no a uno: `ImportacionValidarRequest`,
`ImportacionConfirmarRequest` e `ImportacionPlazoFijoMovimientoRequest`.
`Guid` es un `struct`: un `cuenta_id` ausente se deserializa a
`Guid.Empty` y nunca a `null`, asi que `RequiredAttribute` no podia
fallar. Efecto observable: un campo obligatorio ausente devolvia 404
"Cuenta no encontrada o inactiva" en vez del 400 que corresponde.

Correccion: las tres propiedades pasan a `Guid?` conservando
`[Required]`. En los tres puntos de lectura de `ImportacionService` se
usa `request.CuentaId ?? Guid.Empty` en lugar de `.Value`, para que un
camino interno que no pase por validacion de modelo degrade al 404 ya
existente en vez de lanzar `InvalidOperationException` y convertirse en
un 500.

Fuera de alcance deliberado: `ImportacionLoteCrearRequest.CuentaId`
sigue siendo `Guid` sin `[Required]`. No prometia validacion, luego no
tenia el defecto.

- Build: 0 errores, 6 warnings preexistentes.
- `AtlasBalance.API.Tests`: 427/427. `AtlasBalance.Caching.Tests`: 15/15.
- `dotnet restore --locked-mode -r win-x64` (ruta exacta de

No se ejecuto la aplicacion. El 400 ante `cuenta_id` ausente esta

## Auditoria de ataques de inyeccion: SQLi, XSS, CSRF, path traversal, command injection y open redirect

Auditoria de la superficie de inyeccion completa, pedida sobre siete ejes.
Se ejecuto con seis agentes en paralelo (uno por eje) y cada hallazgo se
valido despues contra el codigo antes de tocar nada. Cuatro de los siete
ejes salieron limpios sin necesidad de cambios.

### Lo que ya estaba bien (verificado, sin cambios)

- **SQL injection.** Cero concatenacion. El SQL crudo de produccion son
  literales con parametros posicionales (`pg_advisory_xact_lock({0})`) o
  `ExecuteSqlInterpolated`, que recibe un `FormattableString` y lo
  convierte en `DbParameter` reales; no es lo mismo que pasar un `string`
  interpolado a la variante `*Raw`, que si seria vulnerable. Los 7
  endpoints con `?sortBy=` resuelven la ordenacion con `switch` de
  literales y `default` seguro. `RlsDbCommandInterceptor` inyecta el
  contexto RLS con `set_config(@param)` parametrizado y firma HMAC.
- **XSS.** Sin `innerHTML`, `dangerouslySetInnerHTML`, `document.write`,
  `eval` ni `new Function` en el frontend. Emails con `HtmlEncode` en cada
  campo; XLSX y CSV con guarda anti-formula. La CSP ya trae `script-src
  'self'` sin `unsafe-inline`/`unsafe-eval`, mas `object-src 'none'` y
  `frame-ancestors 'self'`.
- **Open redirect.** `safeRoute.ts` rechaza absolutas, `//`, `/\`, `\` y
  caracteres de control, y revalida tras `decodeURIComponent`. El backend
  no tiene ningun `Redirect`.
- **Command injection.** Los dos `ProcessStartInfo` usan `ArgumentList`,
  que pasa cada argumento de forma atomica sin re-parsing de shell. La
  password de Postgres va por `PGPASSWORD` en el entorno, no en la linea
  de comandos.

### Hallazgo 1 - `backup_path` y `export_path` aceptaban rutas de red (UNC)

El de mayor impacto. `IsSafeAbsoluteDirectory` rechazaba `..` y exigia ruta
"rooted", pero la comprobacion era:

```csharp
if (!Path.IsPathRooted(trimmed) && !LooksLikeWindowsRootedPath(trimmed))
```

`Path.IsPathRooted(@"\host\share")` devuelve `true` en .NET, asi que una
ruta UNC pasaba por la primera condicion sin llegar nunca al filtro
estricto de `C:\`, y tampoco contiene `..`. Un ADMIN podia por tanto
apuntar `backup_path` a un recurso SMB externo: los `pg_dump` siguientes
—volcado integro de la base de datos, con IBANs, saldos y PII— se
escribian fuera de la maquina de forma persistente y sin ninguna senal.

No es escalada de privilegio (un admin ya puede descargar backups), pero
si es exfiltracion silenciosa y continuada, distinta de una descarga
puntual que queda auditada.

Se anade `IsUncPath` y se sustituye el `OR` por la comprobacion estricta en
los **tres** puntos que validan la ruta: `ConfiguracionController`
(entrada) mas `BackupService` y `ExportacionService`, que releen el valor
desde la tabla de configuracion y por tanto podrian encontrarse un UNC
guardado antes de este cambio. Los mensajes de error de la API pasan a
decir explicitamente que no se admiten rutas de red, para que un admin que
pegue `\nas\backups` entienda el rechazo.

**Decision de producto:** se bloquean las rutas UNC por completo en vez de
permitirlas con auditoria. Quien necesite un NAS puede montarlo como
unidad local.

### Hallazgo 2 - No existia verificacion de Origin/Referer

De las tres comprobaciones de CSRF pedidas, dos ya estaban: tokens en todo
verbo mutador y `SameSite=Strict` en las cuatro cookies. La tercera no
existia: cero referencias a `Origin` o `Referer` en el backend.

Se anade a `CsrfMiddleware`, no como middleware nuevo: es la misma
responsabilidad y evita otro registro en el pipeline. Dos decisiones de
diseno:

1. **Se aplica sin las exclusiones de `ExcludedPaths`**, a proposito. Ahi
   esta el valor: `/api/auth/refresh-token` estaba exento del token CSRF y
   dependia unicamente de `SameSite=Strict`, es decir de que el navegador
   se comporte. Ahora tiene una verificacion server-side.
2. **Se compara contra el origen de la propia peticion**, no contra una
   allowlist fija. Una lista hardcodeada no vale en una aplicacion
   on-premise donde cada instalacion tiene su host; comparar con
   `Request.Scheme://Request.Host` funciona en cualquier despliegue sin
   configurar nada. En Development se admiten ademas los origenes de Vite,
   porque ahi el frontend (5173) y la API (5000) son cross-origin de forma
   legitima.

Si faltan las dos cabeceras se deja pasar: los navegadores mandan `Origin`
en todo POST/PUT/PATCH/DELETE, luego su ausencia no es una peticion
cross-site de navegador, y el token CSRF sigue aplicando. Queda anotado en
el codigo que un proxy inverso que reescriba el `Host` obligaria a activar
`ForwardedHeaders.XForwardedHost`, o el middleware rechazaria todo.

### Hallazgo 3 - Fallback a PATH al resolver PowerShell en el Watchdog

`ResolvePowerShellExecutable` buscaba `powershell.exe` en System32 y, si no
lo encontraba, devolvia `"powershell.exe"` a secas. `CreateProcess`
resuelve un nombre sin ruta buscando primero en el directorio del
ejecutable, y el Watchdog corre como servicio con privilegios altos: un
binario plantado ahi se ejecutaria en su lugar. El fallback casi nunca se
alcanza en un Windows Server sano, asi que la severidad es baja, pero el
arreglo es de tres lineas. Ahora lanza `InvalidOperationException` con
mensaje explicito en vez de arrancar un PowerShell indeterminado.

### F-TLS-001 (MEDIA) - HSTS con los valores por defecto del framework

`Program.cs` llamaba `app.UseHsts()` sin `AddHsts`, asi que la cabecera
efectiva era `max-age=2592000` (30 dias) y **sin** `includeSubDomains`.

Corregido con `builder.Services.AddHsts(...)`: `max-age` de 365 dias e
`IncludeSubDomains = true`.

`Preload = false` **a proposito**: la lista de preload de los navegadores
exige un dominio publico registrable y es practicamente irreversible;
esta app es on-premise y se instala con hostnames de intranet.
`ExcludedHosts` se deja con el default del framework (`localhost`,
`127.0.0.1`, `[::1]`).

**Riesgo operativo que introduce (leer antes de desplegar).** En modo LAN
el certificado es self-signed. Con HSTS activo, Chrome y Edge convierten
el error de certificado en un fallo **no salteable**: desaparece el
"continuar de todos modos". Pasar de 30 dias a 365 convierte un bloqueo
de un mes en uno de un ano, y limpiarlo exige tocar
`chrome://net-internals/#hsts` en cada equipo. Condicion para que esto
sea seguro: el `.cer` tiene que estar en la raiz de confianza de **todos**
los clientes antes de desplegar.

Ojo con `scripts/install-cert-client.ps1`: solo instala la CA de `mkcert`
(camino de desarrollo). Si `mkcert` no esta, se limita a imprimir la ruta
del `.cer` y no lo instala. El comando real esta en
`documentacion.md:209` (`certutil -addstore -f Root ...`) y hay que
ejecutarlo a mano en cada cliente.

### F-TLS-002 (BAJA) - directiva CSP obsoleta

La CSP de produccion enviaba `block-all-mixed-content`, que quedo fuera de
CSP nivel 3: los navegadores actuales la ignoran y Chrome la reporta como
obsoleta en consola. `upgrade-insecure-requests` (que ya estaba) cubre el
caso. Retirada.

### F-TLS-003 (BAJA) - un `<meta>` degradaba el Referrer-Policy real

`frontend/index.html` llevaba
`<meta name="referrer" content="strict-origin-when-cross-origin" />`
mientras el backend enviaba `Referrer-Policy: no-referrer`. El `<meta>`
**no es redundante: gana**. Segun la spec de Referrer Policy, la politica
la fija la cabecera y el elemento `<meta>` la sobreescribe, asi que el
documento de la SPA acababa con la politica mas debil de las dos.

Retirado el `<meta>`. Queda una unica fuente de verdad (la cabecera) y la
politica efectiva pasa a ser `no-referrer`, mas estricta que el
`strict-origin-when-cross-origin` que pedia el checklist. Para una app
on-premise sin enlaces salientes no se pierde nada.

### F-TLS-004 (RECHAZADO) - `X-Frame-Options: DENY` romperia la importacion

El checklist pedia `DENY`; la app envia `SAMEORIGIN`. **`DENY` bloquea
tambien el enmarcado del mismo origen**, y `CuentaDetailPage.tsx:1297`
enmarca `/importacion` en un `<iframe>` dentro del modal de importar
movimientos (`importUrl`, ruta relativa, mismo origen). Con `DENY` ese
modal se queda en blanco.

`SAMEORIGIN` es el valor correcto aqui y es coherente con el
`frame-ancestors 'self'` que ya lleva la CSP. Sin cambio.

### F-TLS-005 (BAJA) - el watchdog aceptaba cualquier certificado en hosts de red

`WatchdogOperationsService.WaitForApiHealthAsync` usaba
`DangerousAcceptAnyServerCertificateValidator` para el health check
posterior a una actualizacion. El guardia `IsLocalHealthUrl` no solo
admite loopback: tambien `Environment.MachineName` y
`MachineName.local`, que **si resuelven por red**. Un atacante en la LAN
capaz de suplantar ese nombre podia presentar su propio certificado y
devolver un `200 OK` falso, con lo que el watchdog daba por buena una
actualizacion rota y se saltaba el rollback.

Corregido: el validador permisivo solo se activa cuando
`healthUri.IsLoopback`. La instalacion por defecto usa
`https://localhost/api/health` (loopback), asi que el camino normal no
cambia.

### Sin cambio, con motivo

- **`UseHttpsRedirection()` es un no-op en modo reverse proxy.** Sin
  endpoint HTTPS ni `ASPNETCORE_HTTPS_PORT` (ninguno de los dos existe en
  el repo), el middleware no puede resolver el puerto y deja pasar la
  peticion tras loguear un warning. No es explotable: Kestrel escucha
  solo en `127.0.0.1` y Caddy ya redirige. Se deja porque en modo LAN si
  funciona y quitarlo empeoraria ese caso.
- **`Permissions-Policy` no se amplia.** Lo pedido (camera, microphone,
  geolocation) ya estaba. Se descarto anadir `usb`, `serial`, `hid`,
  `midi`, `display-capture` e `idle-detection`: con `script-src 'self'`
  sin `unsafe-inline` la via de ataque practica ya esta cortada, varios de
  esos nombres no los reconocen todos los navegadores y generan ruido en
  consola. **No se puede anadir `clipboard-write=()`**:
  `TokenCreatedModal.tsx:37` usa `navigator.clipboard.writeText` para
  copiar el token de integracion.
- **La CSP duplicada en `<meta>` de `index.html` se queda.** Se aplican
  ambas (la efectiva es la interseccion) y la del `<meta>` no es mas
  laxa, asi que no hay agujero. Queda anotado como riesgo de divergencia:
  si alguien relaja la cabecera y olvida el `<meta>`, el sintoma sera un
  recurso bloqueado sin causa aparente.
- **Cookie CSRF sin `HttpOnly`.** Es el patron double-submit: el frontend
  tiene que leerla para reenviarla en `X-CSRF-Token`
  (`App.tsx:45`). Lleva `Secure` + `SameSite=Strict` y no transporta
  ningun dato de sesion.

### Inventario de cookies

| Cookie (produccion) | Nombre en dev | HttpOnly | Secure | SameSite | Path | MaxAge | Contenido |
|---|---|---|---|---|---|---|---|
| `__Host-atlas-access-token` | `access_token` | si | si | Strict | `/` | 1 h | JWT de acceso |
| `__Host-atlas-refresh-token` | `refresh_token` | si | si | Strict | `/` | 7 d | refresh token |

`Secure` sale de `ShouldUseSecureCookie()` (`AuthController.cs:312`):
siempre `true` fuera de Development. Ninguna cookie lleva `Domain`.

### Invariante nuevo bajo test: el prefijo `__Host-`

`BuildCookieOptions` (`AuthController.cs:300`) **no asigna `Path`**: se
apoya en el default de `CookieOptions`. Eso es fragil, porque el
navegador **rechaza** una cookie `__Host-` que no lleve exactamente
`Path=/`, sin `Domain` y con `Secure`. Si ese default cambiara o alguien
tocara esas opciones, el login entero se romperia en produccion de forma
silenciosa y sin error en el servidor.

`TransportSecurityTests.cs` (nuevo) fija el invariante ejercitando el
`Response.Cookies.Append` real via `AuthController.RefreshToken` en
entorno `Production` y asertando sobre el `Set-Cookie` emitido: `path=/`,
`secure`, `httponly`, `samesite=strict` y ausencia de `domain=` en las
cookies de sesion; y para la de CSRF, lo mismo pero **sin** `httponly`.

## Alcance aplicado - Seudonimizacion del contexto enviado a la IA

### Motivo

Auditoria de datos personales (PII) sobre la aplicacion. El hallazgo mas
grave fue que `AtlasAiService` enviaba al proveedor de IA externo el nombre
del titular, el nombre de la cuenta y el concepto integro de cada
movimiento. La unica proteccion existente era `RedactIbanLike`, que solo
redacta IBANs; `SanitizeContextText` unicamente recorta a 180 caracteres,
no anonimiza. Ademas la garantia de no retencion (`zdr=true`,
`data_collection=deny`) solo se aplica en la rama de OpenRouter: con
OpenAI o MiniMax los datos salian sin ninguna garantia.

Decision del propietario: mantener la funcion (poder preguntar por saldos
y extractos y recibir respuesta util) pero impedir que el proveedor pueda
saber a quien pertenecen los datos aunque los retenga.

### Que se ha hecho

Seudonimizacion **reversible** en `AiPseudonymMap` (nuevo,
`Services/AiPseudonymizer.cs`):

- Se construye por peticion con las entidades del scope del usuario:
  nombres de titulares, de cuentas y de terceros de los desgloses
  (`ExtractoDesglose.TerceroNombre`).
- `Apply` sustituye los nombres reales por `[TITULAR_n]`, `[CUENTA_n]`,
  `[TERCERO_n]`; `Reverse` deshace la sustitucion.
- Se aplica **a la pregunta y al contexto**. Anonimizar solo el contexto
  no habria servido de nada: la pregunta del usuario lleva los nombres
  reales y el proveedor habria reconstruido el mapeo de inmediato.
- La respuesta del proveedor se revierte antes de mostrarla, de modo que
  el usuario sigue viendo los nombres reales.
- `BuildFinancialContextAsync` sigue recibiendo el prompt REAL a
  proposito: busca en BD por terminos de la pregunta. Solo se
  seudonimiza lo que sale hacia el proveedor.

Decisiones tecnicas relevantes:

- **Una sola pasada de regex con alternancia**, no una pasada por nombre.
  Con pasadas sucesivas, una entidad llamada "Cuenta" reescribe el
  interior del placeholder `[CUENTA_1]` ya insertado y el texto queda
  corrupto e irreversible. Cubierto por el test
  `AiPseudonymMap_Apply_Should_Not_Corrupt_Placeholders_Already_Inserted`.
- Alternativas ordenadas por longitud descendente: la alternancia de .NET
  es leftmost-first, asi "Acme Solutions SL" gana sobre "Acme".
- Limites `(?<![\p{L}\p{N}])` / `(?![\p{L}\p{N}])` para no partir
  palabras ("Ana" no debe alterar "Anabel").
- Nombres de menos de 3 caracteres descartados, para no sustituir "SL".
- **Fail-closed**: si el regex agota el timeout (2 s), `Apply` propaga
  `RegexMatchTimeoutException`, `AskAsync` la audita como
  `pseudonymization_timeout` y aborta la consulta. En un control de
  privacidad, fallar es preferible a enviar nombres reales.
- La auditoria registra `entidades_seudonimizadas` (recuento). Nunca el
  mapa ni los nombres reales.

### Limitacion conocida

Los nombres de terceros que aparezcan **incrustados en texto libre** de un
concepto y que no correspondan a ninguna entidad registrada no se
sustituyen: no son enumerables. Se cubren los que si estan registrados
como titular, cuenta o tercero de desglose.

implementarlo aqui sale mal:

1. **Rompe funcionalidad.** `USUARIOS` se lee desde unos ocho sitios para
   resolver nombres a mostrar (`ExportacionesController:93`,
   `DashboardService:856`, auditoria, alertas, backups). Una politica de
   "cada usuario solo su fila" vaciaria esos nombres para los no-admin.
2. **El login necesita una via de escape.** La autenticacion busca por email

   tendria que poder leer toda la tabla. La politica se queda en poco mas que
   "permitir a cualquier contexto firmado".
3. **Lo que protegeria ya esta cubierto.** Ni `password_hash` ni `mfa_secret`

El RLS de este proyecto esta disenado para segregacion multi-titular del
dominio financiero, y ahi funciona bien (23 tablas). Extenderlo a identidad y
autenticacion es coste y riesgo de regresion a cambio de un margen de
seguridad muy fino. Si aun asi se quiere, hay que hacerlo como trabajo propio
con su bateria de pruebas de login, no como remate de esta auditoria.

## Alcance aplicado - Anonimizacion hacia IA y hacia OpenClaw

Requisito del propietario: ni la IA ni OpenClaw deben poder ver el IBAN, y el
nombre de titular y de cuenta debe salir anonimizado en ambos, pero sin perder
la capacidad de preguntar por ellos y obtener la respuesta correcta.

### Estado previo

| | IBAN / nº cuenta | Nombre titular y cuenta |
|---|---|---|
| IA | nunca se enviaba (ya correcto) | seudonimizado reversible (ya correcto) |
| OpenClaw | enmascarado, ultimos 4 visibles | **en claro** |

En la IA ya estaba resuelto por el bloque anterior. Se verifico ademas que el
IBAN no entra siquiera en el contexto: `BuildFinancialContextAsync` no lo
proyecta, y `RedactIbanLike` queda solo como red de seguridad por si un IBAN
aparece dentro del texto libre de un concepto.

### Diferencia arquitectonica entre los dos casos

Con la IA, Atlas Balance es el intermediario: envia el seudonimo, recibe la
respuesta y la revierte antes de mostrarla. El proveedor nunca ve el nombre y
el usuario nunca ve el seudonimo.

Con OpenClaw no lo es: OpenClaw llama a la API y luego habla con su usuario por
su cuenta, asi que Atlas Balance no puede revertir nada en su lado. Por eso la
solucion es distinta: seudonimo estable + resolucion bajo demanda.

### Cambios en OpenClaw

- **IBAN y numero de cuenta eliminados por completo** de toda la superficie de
  la integracion. No se enmascaran: no se envian. Se retiraron tambien las
  propiedades de `ScopedCuentaInfo` que los transportaban.
- **Nombres sustituidos por seudonimos opacos y estables**
  (`Services/IntegrationPseudonyms.cs`): `TITULAR-a3f2b901`, `CUENTA-7b10c204`,
  derivados de los 8 primeros hex del GUID de la entidad. El GUID completo ya
  viajaba en el campo `id`, asi que el seudonimo no anade informacion: es solo
  una etiqueta opaca y estable. Sin secreto ni hashing, porque no aportarian
  nada frente a un dato que el consumidor ya tiene.
- **Ordenaciones cambiadas** para ordenar por el seudonimo y no por el nombre
  real. Ordenar por nombre real devolviendo etiquetas opacas habria filtrado el
  orden alfabetico, que es justo lo que el formato opaco evita.
- **Nuevo `POST api/integration/openclaw/resolver-nombres`**: resuelve el nombre
  real de titulares y cuentas bajo demanda. Aplica el scope del token
  (`GetScopedAccountsAsync`); un id fuera de scope simplemente no aparece en la
  respuesta, sin distinguir "no existe" de "no autorizado", para no convertirlo
  en un oraculo de existencia. Tope de 200 ids por lote. Auditoria explicita con
  el NUMERO de ids resueltos, nunca los nombres ni los ids: el middleware de
  integracion solo serializa la query string, no el body de un POST.

### Limitacion importante, a tener en cuenta al construir OpenClaw

El endpoint de resolucion existe porque se pidio que OpenClaw pudiera saber de
quien son los datos. Eso implica que **si OpenClaw resuelve un nombre y lo mete
en el prompt de su propio LLM, la anonimizacion se pierde en ese punto**, y
Atlas Balance no puede evitarlo.

La proteccion funciona si OpenClaw resuelve solo para mostrar a una persona, no
para alimentar al modelo. El valor real de este diseno es que el corpus masivo
que un proveedor pudiera retener queda anonimo, y que cada re-identificacion
deja rastro en la auditoria.

El tope de 200 ids no impide una re-identificacion masiva a base de llamadas
pequenas; lo que hace es dejarla visible en la auditoria.

## Logging, monitorizacion y trazas de auditoria (2026-07-30)

Ultimo bloque de la tanda de seguridad de V-02.07. Detalle tecnico completo en
`DOCUMENTACION_TECNICA.md`, seccion "V-02.07 - Logging, monitorizacion y trazas
de auditoria".

### Que se pidio y que habia

De los cuatro bloques del encargo, buena parte del primero ya estaba resuelta:
auditoria automatica de 28 entidades con valores antes y despues dentro de la
misma transaccion del negocio, eventos de login con IP y motivo, Serilog con
niveles y rotacion, y redaccion de PII en logs. La revision de fugas (bloque 4)
salio **limpia**: ningun log vuelca passwords, tokens, cookies ni cuerpos de
peticion.

Lo que faltaba, y es lo que se ha hecho:

1. **Los fallos de autorizacion no dejaban rastro.** Habia unos 40 `Forbid()`
   repartidos por los controladores y ninguno se auditaba. Un usuario legitimo
   probando ids de cuentas ajenas era completamente invisible.
2. **La auditoria no tenia contexto ni era verificable.** Sin User-Agent (se
   recibia en el login y se descartaba), sin id de sesion, sin distinguir si la
   accion entro por el navegador o por la API, y sin nada que permitiera
   afirmar que una fila no habia sido alterada.
3. **La retencion era de 28 dias.** Para tesoreria multi-banco no cubre ni un
   cierre trimestral.
4. **No existia ninguna alerta de seguridad.** El servicio de alertas era de
   negocio (saldos bajos).
5. **`/api/health` mentia.** Devolvia `{status:"healthy"}` constante, sin tocar
   base de datos ni disco. Eso es peor que no tener health check.
6. **`/api/sistema/actualizar` no se auditaba**, siendo la accion de admin con
   mas alcance de toda la aplicacion.

### Lo mas relevante del resultado

**La auditoria ahora se puede usar como prueba.** Cada fila lleva firma
HMAC-SHA256 con clave propia (distinta de la de JWT y de la de RLS) y una
secuencia monotonica de Postgres. Alterar una fila rompe su firma; insertar una
falsa es imposible sin la clave; borrar filas deja un hueco en la secuencia. Se
verifica bajo demanda (`GET /api/auditoria/integridad`) y una vez al dia de
forma automatica.

**Append-only de verdad y ruidoso.** El rol de aplicacion tiene revocados
UPDATE, DELETE y TRUNCATE sobre `AUDITORIAS`, y como no es el propietario no
puede reconcederselos. Un trigger bloquea cualquier UPDATE y el borrado de
cualquier fila de menos de 90 dias, incluso por la via sancionada. La unica forma
de purgar es una funcion `SECURITY DEFINER` con ese suelo validado dentro de la
base de datos.

**Se encontro un bug preexistente serio de camino.** `LimpiezaAuditoriaJob`
llevaba desde V-02.03 borrando cero filas cada noche y registrandolo como exito,
porque RLS sin politica de DELETE filtra las filas en silencio. La tabla crecia
sin limite. Cerrado y documentado en `LOG_ERRORES_INCIDENCIAS.md`.

**Seis reglas de alerta** sobre la auditoria, con enfriamiento de 60 minutos y
entrega por auditoria, notificacion de admin, email y Slack (opt-in). Los avisos
de salud (picos de 5xx, degradacion de latencia, disco o base de datos en rojo)
usan el mismo canal.

### Dos cosas que no se hicieron como pedia el enunciado, y por que

**"Alertar de login desde un pais nuevo" es "alertar de IP nueva".** No hay
GeoIP: la aplicacion es on-premise, en LAN, sin salida garantizada a internet.
Una base de geolocalizacion seria una dependencia externa imposible de mantener
actualizada. La IP captura la misma senal en este despliegue.

**No hay pagina de estado dentro de la aplicacion.** Una pagina de estado
servida por el mismo servicio que se cae no informa de nada justo cuando mas
falta hace. Lo que se ha hecho es exponer `/api/sistema/salud` con codigo 503
cuando algo esta mal, para que un monitor externo lo consuma.
`DOCUMENTACION_TECNICA.md` recomienda Uptime Kuma, que trae pagina de estado y
notificaciones sin coste.

### Limite honesto del diseno

Todo lo anterior protege frente a **una aplicacion comprometida**, que es el
escenario realista: inyeccion, abuso de credenciales de usuario, o el propio
connection string de runtime en manos equivocadas.

No protege frente a quien consiga las credenciales del rol propietario de la
base de datos, superusuario de PostgreSQL, o ejecucion de codigo como SYSTEM en
el servidor (el servicio corre como LocalSystem, asi que puede borrar el fichero
de log de seguridad y vaciar el Windows Event Log).

Para ese escenario la unica defensa real es **sacar los logs de la maquina**. Se
deja documentado con opciones concretas, empezando por el reenvio de eventos de
Windows, que viene incluido en el sistema operativo. Es decision de despliegue,
no de codigo, y por eso no se fuerza desde el instalador.

### Verificacion

Suite completa: **555/555 correctas**, con Docker disponible, asi que tambien
los tests con Testcontainers. Se anadieron 9 tests que corren contra PostgreSQL
16 real (`AuditoriaAppendOnlyPostgresTests`) porque lo que hace append-only a la
tabla vive en SQL y con EF InMemory pasaria sin ejecutarse. El mas importante
comprueba que una fila firmada sigue validando despues del viaje de ida y vuelta
a la base de datos: es donde se rompen las suposiciones sobre precision de
timestamp (Postgres guarda microsegundos, .NET 100 ns) y normalizacion de JSON
(`jsonb` reordena claves, por eso la columna paso a `json`).
