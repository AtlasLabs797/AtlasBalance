## Cache cliente de TanStack Query (V-02.07 F-PERF-008)

### Alcance

Auditoria V-02.02 (`AUDITORIA_GENERAL_MAVIS_V-02-02.md:220`) recomendo
introducir un helper `useFetcher` con `AbortController` para todos los
listados y un cache de Dashboard a 30 s. La auditoria frontend reciente
(78 `api.get` en `frontend/src/**`, ver `DOCUMENTACION_CAMBIOS.md` entrada
del 2026-07-28) confirmo que las paginas del `<Outlet>` se desmontan al
navegar y que `StrictMode` duplica los efectos de montaje sin
deduplicacion. Esto generaba storms al volver a una pantalla, re-fetch
de agregados de dashboard al alternar entre `Dashboard`, `Titulares` y
`Cuentas`, y re-fetch del resumen de cuenta al paginar.

Se adopta `@tanstack/react-query@^5.59.0` como capa de server-state en
memoria. Es la opcion minima coherente con los 78 GET y 78 mutaciones
existentes: una cache artesanal distribuida por componentes terminaria
siendo peor que la libreria. Se mantiene Axios y sus interceptors
(cola de refresh JWT, CSRF, toast de 5xx/red caida) tal cual.

### Cambios

1. **Dependencia**: `@tanstack/react-query@^5.59.0` añadida a
   `frontend/package.json` y al `package-lock.json`. Bundle adicional
   ~13 KB gzip (entra al chunk `index` actual, sin nuevo chunk).

2. **`frontend/src/services/queryClient.ts`**: `QueryClient` singleton

## Cierre #16 - React Router SSR deserialization (GHSA-337j-9hxr-rhxg) + #17 open redirect (GHSA-wrjc-x8rr-h8h6)

### Alcance

Vulnerabilidades #16 y #17 del registro de seguridad. React Router 6.30.4

2. **`package-lock.json` regenerado** tras apartar `node_modules` al

   node-modules-blocked-2026-07-24-v0207`) para esquivar el `EPERM`

   `frontend/src/utils/safeRoute.ts` con

## Cache de lecturas repetidas del dashboard

### Alcance

Recomendacion del check-list de rendimiento:

> "Cache repeated read queries. Identify read queries that run very
> frequently with the same or few distinct parameters and return data
> that changes slowly. Add a caching layer in front of them with keys
> based on the query parameters and TTLs matched to the data's
> volatility, plus invalidation on relevant writes. Ensure cache misses
> populate safely under concurrency. Verify database query volume for
> these reads drops sharply and response times improve."

Implementacion acotada al dashboard y al catalogo de tipos de cambio.
No se cachean respuestas HTTP completas: se cachean los snapshots
internos que ya estaban costando varios SELECTs identicos por carga
del dashboard. Esto evita los riesgos de claves incompletas que
romperian el aislamiento por usuario (`paisId`, `divisa`, `titularId`,
`userId`, `puedeVerDashboard`).

### Cambios

1. **Nueva capa de cache en proceso (`AtlasBalance.API/Caching/`)**:

   - `ICacheService` + `CacheService`: `IMemoryCache` con
     `GetOrLoadAsync<T>` que implementa single-flight (un `SemaphoreSlim`
     por namespace+key) y generaciones (cada escritura bumpea un
     contador por namespace y las claves cacheadas quedan
     automaticamente invalidadas sin enumerar el cache). Sin entradas
     de timeout porque la generacion las invalida antes.
   - `CacheMetricsSnapshot` con hits, misses, loads, single-flight waits,
     invalidations, load failures. Se expone por namespace via
     `ICacheService.GetMetricsSnapshot(string)`. No contiene claves ni
     IDs para evitar leakage a logs.
   - `DashboardCacheInvalidator`: fachada con tres metodos
     (`InvalidateDashboardScope`, `InvalidateDashboardReference`,
     `InvalidateDashboardMetrics`) que invalida los namespaces del
     dashboard de forma centralizada.

2. **Single-flight + generaciones aplicadas a `TiposCambioService`**:

   El catalogo de tasas ya estaba cacheado (`IMemoryCache`, TTL 5 min,
   invalidacion tras guardado manual o sincronizacion API), pero
   `AUDITORIA_CONCURRENCIA_2026-07-10.md:302` (CONC-027) documentaba
   una race benigna entre `InvalidateCache()` y la llamada a `_cache.Set`
   que podia repoblar datos viejos. La nueva implementacion:
   - usa `GetOrLoadAsync` con lock por namespace+key, asi dos requests
     concurrentes con cache miss ejecutan UN solo `SELECT` sobre
     `TIPOS_CAMBIO`.
   - bumpea la generacion del namespace tras cada escritura manual
     (`GuardarTipoCambioManualAsync`) y sincronizacion API
     (`SincronizarTiposCambioAsync`), lo que invalida todas las entradas
     cacheadas sin enumerarlas.
   - tambien invalida el namespace `dashboard_metrics` porque las
     metricas convertidas dependen del catalogo de tasas.

3. **Scope del dashboard cacheado por usuario**:

   `DashboardService.GetAuthorizedScopeAsync` envuelve el calculo en
   `GetOrLoadAsync(new CacheNamespace(ScopeNamespace), userId:N,
   loader, TTL=30s)`. Las tres llamadas paralelas del frontend
   (`/dashboard/principal`, `/dashboard/evolucion`,
   `/dashboard/saldos-divisa`, ver `DashboardPage.tsx:161`,
   `CuentasPage.tsx:313`, `TitularesPage.tsx:195`) ahora resuelven el
   scope UNA vez por TTL. Claves normalizadas (`userId` en formato
   hex) para evitar fuga entre usuarios.

4. **Referencia del dashboard (divisa base + colores) cacheada**:

   `LoadReferenceAsync` cachea la combinacion `divisa_base + colores`
   durante 5 min. La clave es fija por namespace (`default`) y la
   generacion se invalida cuando cambian `DIVISAS_ACTIVAS` o las claves
   de configuracion relevantes (`divisa_principal_default`,
   `dashboard_color_*`).

5. **Metricas del dashboard cacheadas entre endpoints**:

   `GetOrBuildMetricsAsync` envuelve `BuildMetricsAsync` con TTL de
   15 s y clave `userId|paisId|divisa|hashCuentas`. Asi `principal` y
   `saldos-divisa` (que recalculaban lo mismo) ya no duplican el
   trabajo de agregar extractos por cuenta/divisa ni la conversion
   bulk de tasas.

6. **Invalidacion centralizada via `DashboardCacheInvalidationInterceptor`**:

   Nuevo `SaveChangesInterceptor` registrado tras `AuditSaveChangesInterceptor`
   que invalida caches de dashboard despues de un `SaveChanges`
   exitoso si entre las entidades tocadas estan:
   - `Extracto`, `ExtractoColumnaExtra`, `ExtractoDesglose`,
     `Cuenta`, `PlazoFijo`, `TipoCambio`, `DivisaActiva`,
     `Configuracion` (solo claves relevantes) -> invalida metricas.
   - `PermisoUsuario`, `PreferenciaUsuarioCuenta`, `Usuario`,
     `Cuenta`, `Titular`, `Pais` -> invalida scope.
   - `DivisaActiva`, `Configuracion` (claves relevantes) -> invalida
     referencia.

   Asi cualquier ruta de escritura (controllers, jobs Hangfire,
   seeds) queda cubierta sin acoplar `IDashboardCacheInvalidator`
   en cada consumer. Cobertura minima para no inflar AUDITORIAS ni
   invalidar por escrituras no relacionadas (SMTP, secretos, etc.).

7. **Tests** (`backend/tests/AtlasBalance.Caching.Tests/`, proyecto
   nuevo para no tocar el de tests preexistente que arrastra errores
   de compilacion V-02.06):

   - `CacheServiceTests` (6 facts): hits, single-flight con 20
     lectores concurrentes, generacion por namespace, aislamiento
     entre namespaces, race invalidar durante carga, propagacion de
     cancelacion.
   - `CacheIntegrationTests` (3 facts): invalidacion del catalogo de
     tasas tras escritura manual, bump de generaciones al invalidar
     scope y metrics, consistencia del cache de scope tras cambio
     conceptual de permisos.

   - Clave: `config:all:v1` (un unico entry por TTL).
   - Invalida: `ConfiguracionRepository.UpsertAsync` (cualquier
     escritura al namespace) y como red de seguridad el
     `DashboardCacheInvalidationInterceptor` ante cualquier save
     changes sobre `Configuracion`.

3. **`IUserAccessService.GetScopeAsync`** (CONC-028 cerrado):

   Cachea el calculo del `UserAccessScope` por `userId` con TTL
   45 s. Bypass explicito para admin: el resultado es trivial y
   queremos que un cambio de rol puntual quede visible sin esperar
   al TTL (la rotacion de `SecurityStamp` ya invalida el JWT en el
   middleware).

   - Clave: `userId:N`.
   - Invalida: cambio en `PermisoUsuario`/`PreferenciaUsuarioCuenta`
     via interceptor, mas red de seguridad por rotacion de
     `security_stamp` del usuario.

4. **`IIntegrationTokenService.ValidateActiveTokenAsync`**:

   Cachea el token activo por `TokenHash` con TTL 20 s. OpenClaw
   puede llegar a 100 req/min del mismo token sin golpear BD.

   - Clave: `sha256(plainToken)`.
   - Invalida: `RevokeAsync` (namespace completo tras SaveChanges,
     ventana maxima 20 s) y el interceptor ante cualquier save
     changes sobre `IntegrationToken` (rotacion en
     `IntegracionesController.cs:284`).

5. **`IAuthService.GetCurrentAsync`**:

   Cachea el `AuthResult` de `GET /api/auth/me` con TTL 60 s y clave
   compuesta `(userId:N)|{securityStamp}`. Una rotacion de stamp
   invalida la entrada por la propia clave, sin pasar por el
   interceptor. El interceptor anade una capa defensiva para
   cambios en `USUARIOS`, `PERMISOS_USUARIO` o
   `PREFERENCIAS_USUARIO_CUENTA`.

   - Clave: `userId:N|securityStamp`.
   - Invalida: red de seguridad via interceptor (3 entidades).

6. **`DashboardCacheInvalidationInterceptor` ampliado**:

   Tres nuevos grupos invalidados:
   - `EntidadesQueInvalidanConfiguracion = { Configuracion }` ->
     invalida `ConfiguracionRepository.Namespace`.
   - `EntidadesQueInvalidanAuthCurrent = { Usuario, PermisoUsuario,
     PreferenciaUsuarioCuenta }` -> invalida `AuthService.AuthCurrentNamespace`.
   - `EntidadesQueInvalidanIntegrationToken = { IntegrationToken }`
     -> invalida `IntegrationTokenService.Namespace`.

   Ademas, `EntidadesQueInvalidanScope` ahora tambien invalida
   `UserAccessService.Namespace` (no solo `dashboard_scope`), por
   consistencia con la regla "scope del usuario cambia en cualquier
   mutacion de permisos/relacion/usuario".
